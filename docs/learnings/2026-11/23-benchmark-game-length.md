## 2026-11-23: A benchmark game that ends at a different turn reads as a speed change
- **The nightly flagged the median AI turn 22 to 25% slower (27 to 33 ms) and a per-commit run pinned it on #109 (`treasury_build_guard`). It was not a slowdown.** Before #109 the benchmark game (`ai_budget 7000001 200 hard`) ended near turn 168; after it the game runs all 200 turns. Turns 0 to 150 cost the same on both sides; the extra 32 late turns are the heaviest, so the median and the total rose with no code getting slower.
- **What disproved the first guess:** `planned_net_gold` looked guilty by reading (it walks units, cities and orders, and `troop_unfunded` calls it per candidate). Timed directly it was about 40,000 calls and under 10 ms in the whole game. Read the cost before blaming the code that changed.
- **Fix:** `tools/perf/lean_check.py` now takes p50 and p95 over the turns both sides played and records `ai_turns_played`, so a change in game length shows as that and not as slower turns. The same effect probably explains part of `sim_eight_cpu_s` moving across rule changes (not verified): cpu-s per game is not comparable when the digest moved.
- **When a timing moves with the hash:** split the game into turn ranges and compare range by range before naming a commit.
